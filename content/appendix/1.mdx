# 把 Racket 嵌进原生应用——嵌入式运行时的通用模式

> 你已经读完了一整本书的 Racket。这一篇回答一个收官问题：Racket 能不能不住在自己的 REPL 里，而是住进别人家的应用——一个 Swift 写的 macOS 应用、一个 C++ 写的 Windows 程序？答案是能。这一篇把「嵌入式运行时」的核心技术一次讲透：运行时怎么装进进程、值怎么跨过语言边界、粘合代码怎么不用手写。

## 为什么要“嵌”

假设你要写一个真正的桌面应用：界面要原生、要快、要符合平台的操作习惯；而业务逻辑——数据加工、领域规则、自动化流程——你想用 Racket 写。工程上有三条路。

**第一条：外部进程。** Racket 程序独立运行，UI 程序通过管道或 socket 跟它说话。实现最简单，但代价是两个进程的生命周期要手动对齐：谁先启动、崩溃了谁拉起、升级时怎么搭配版本，全变成你要操心的事。

**第二条：HTTP 服务。** Racket 起一个 Web 服务器（卷七第 53 章你亲手写过），UI 当客户端。这条路上手也不难，但每一次数值交互都隔着网络栈的编解码，本机回环也不例外；而且让用户机器上常驻一个监听端口的服务，分发和维护都变重了。

**第三条：进程内嵌入。** 把 Racket 运行时直接加载进应用的进程，让它和 UI 共享同一个内存空间、同一个生命周期。没有部署拓扑，没有网络往返，启动即可用——代价是你要真正理解「运行时」是什么。

这条路已经有人走通了：把整个 Racket VM 装进一个 iOS 应用，让 Swift 和 Racket 互相对话，是完全可行的事。下面把它的核心技术拆开讲。

## 运行时的三件套

先回答最底层的问题：一个 Racket 程序跑起来，到底需要哪些东西？拆开任何一个 Racket 发行版，嵌入所需的内核只有三样。

**运行时库。** Racket CS 体系下就是一个静态库——`libracketcs-<架构>-<平台>.a`（比如 `libracketcs-arm64-macos.a`），里面装着 Chez Scheme 虚拟机、Racket 核心运行时和 C API 的全部实现。你的应用链接它，运行时就住进了进程。

**头文件。** `racket.h`、`racketcs.h` 和 `racketcsboot.h` 这组声明，定义了宿主能对运行时做的每个动作：求值、应用函数、加载文件、启动 VM。以 C 为宿主语言时直接 `#include`；Swift 这样的语言也能通过桥接头文件直接看到这些 C 函数签名，当成普通函数调用。

**Boot 文件。** 这是最容易被忽略的一样：一组 `.boot` 文件——`petite.boot`、`scheme.boot`、`racket.boot`。它们是 VM 的「启动镜像」：编译好的字节码、初始数据结构、核心库。没有它们，运行时就是一个空壳，连一个表达式都求值不了。

三件套的版本必须**精确匹配**——boot 文件和静态库是同一个编译产物的两半，混用版本会在启动时以神秘的方式崩溃。嵌入方案要做的第一件事，就是把「用哪个 Racket」变成构建期的显式依赖，钉死版本，绝不退而求其次。

## 启动：把 VM 拉起来

三件套就位后，启动序列是固定的四步。用 C 的口吻写出来大概是这样：

```c
// 1. 准备启动参数：exec 文件名 + 三个 boot 文件的路径
racket_boot_arguments_t args;
args.exec_file  = "racket";
args.boot1_path = ".../petite.boot";   // Petite Scheme 基础镜像
args.boot2_path = ".../scheme.boot";   // 扩展为完整 Scheme
args.boot3_path = ".../racket.boot";   // 加载 Racket 语言特性

// 2. 启动 VM：依次读入三个镜像，堆和基础库就位
racket_boot(&args);

// 3. 载入你的应用代码——提前用 raco 编译好的字节码（.zo）
racket_embedded_load_file("/path/to/app.zo", 1);

// 4. 取出模块里的函数，构造参数，调用
ptr f = racket_primitive("app-main");
ptr result = racket_apply(f, argument_list);
```

注意 boot 文件是**运行时**加载的，不是编译期：宿主启动时按平台找到自己的那份镜像（iOS 真机和模拟器的就不同），逐层读入——先 Petite 基础镜像，再完整 Scheme，最后 Racket 层——堆初始化完成，VM 才进入可运行状态。你的应用代码则应该提前用 `raco make` 编译成 `.zo` 字节码，随应用打包，启动时一次载入。

还有一条纪律，每个平台都要遵守：**所有 Racket 操作必须在初始化 VM 的那个线程上执行。** Racket 的垃圾回收器和线程调度假定自己独占一个线程；宿主可以从任何线程发起请求，但请求要在边界上排队，由 VM 线程执行——激活、执行、停放，配对成对出现。谁在回调里随手跨线程调 `racket_apply`，谁就会见到最难查的崩溃。

## 跨过边界：值与内存

VM 跑起来了，接下来是让两边的值互相来往。这一层比想象中琐碎，因为两种语言对「数据」的世界观不同。

Racket 这边，一切皆值：列表、符号、精确有理数、结构体。宿主那边，Swift 有 `Int64` 和 `String`，C++ 有 `int64_t` 和 `std::string`——没有列表，没有符号，整数还有宽度。所以每一次跨界，值都要被**编组**（marshal）：Racket 的整数变成宿主的定宽整数，字符串统一约定 UTF-8 编码，复合数据要么拆成平铺的字段，要么序列化成字节流再在另一侧重建。

底层的机制值得看一眼：宿主侧拿到的 Racket 值，本质是一个指向 Racket 堆的指针（C 类型 `ptr`）。它由 Racket 的垃圾回收器全权管理，宿主的包装只是借眼看——不拥有、不释放、不过夜。这直接引出编组层的第二条纪律：**内存归属必须显式约定。**要么值传递（复制过界，各自管各自的），要么引用传递时配对显式的生命周期管理。省略这个约定，等来的就是野指针或内存泄漏，而且是「有时才崩」的那种。

把这些纪律集合起来，编组层的职责清单就三行：**类型翻译、内存归属、错误传播**。手写当然可行，但每个函数的两端各写一遍参数拆装，枯燥且容易错——所以现代方案都选了同一条路：不手写，生成它。

## 契约先行：让宏生成粘合层

这是全部模式里最值得你带走的一个，因为它把卷六学的宏系统变成了工程生产力。

思路是：**用一套声明式宏把「两端共享的接口」写成一份契约，再由宏展开生成两端的粘合代码。**一套典型的契约 DSL 长这样：

```racket
;; 数据结构：一次计算日志
(define-record OperationLog
  [operator : String]
  [operand1 : Float64]
  [operand2 : Float64]
  [result   : Float64])

;; 过程：宿主可以调用的 RPC，签名即契约
(define-rpc (calculator-add [a : Float64] [b : Float64] : Float64)
  (+ a b))
```

这两个「宏」在展开期做的事情，你在卷六全都写过雏形：用 `syntax-class` 解析字段语法，提取字段名、类型、可选性；据此生成 Racket 侧的 `struct` 和访问器；生成描述这份形状的**元数据**并注册到全局表——元数据就是后续一切代码生成的依据；最后生成序列化和反序列化代码。宿主侧的粘合层由工具从同一份元数据生成：`calculator-add` 在 Swift 侧变成一个普通的强类型函数 `func calculatorAdd(a: Double, b: Double) -> Double`，编组、传输、错误传播全部由生成的代码接管。

传输本身不需要花哨：两个进程内世界的边界，用应用自己的 stdin/stdout 或一对文件描述符就够了。消息编码成二进制（定宽整数、UTF-8 字符串、长度前缀的帧），请求带 id，响应配对，事件单向推送。在这套基础上，异步也自然成立——慢操作在 Racket 侧跑，宿主不等结果，完成时以事件回推。

回头看这条技术路线，它其实是本书主线的一次收束：**宏系统是「协议工程学」的底座。**语言可定制（卷六）意味着接口描述本身也可以是一门为跨语言定制的小语言——契约即代码，粘合层即宏展开的产物。声明一份契约，两端独立进化：后端重构内部实现，契约不动，宿主一行不改；UI 换掉整个框架，Racket 后端浑然不觉。

## 分发：平台 × 架构的乘法

模式讲完，剩下的是工程现实：你的应用要跑在用户的机器上，而用户的机器是 x86_64 或 ARM64，是 macOS、Windows 或 Linux。

嵌入式方案的分发矩阵因此是「平台 × 架构 × 运行时」的三维乘法：每个目标都要有对应的运行时库和 boot 文件，宿主二进制也要按目标编译。Apple 平台的答案是 XCFramework——把各架构的静态库和头文件打成单个可分发的框架；其他平台则直接按目标链接对应的静态库。共同的思路是把「编译 Racket 运行时 → 编译应用字节码 → 集成进宿主 → 出应用包」写成 CI 流水线，每个目标一组产物，发布时一次性出齐。

对比一下这条路的两个时代：早些年嵌入一个 Lisp 运行时是 C 层的冒险，每一步都要自己摸索；今天它需要的全部原料——静态库、头文件、boot 文件——都是 Racket 发行版自带的产物，`raco make` 负责字节码，剩下的只是把它们装配起来。**基础设施成熟的意义就在这里：让下一批人从「打通链路」直接跳到「解决问题」。**

## 工程检查清单

把这一篇的模式收拢成一张清单，供你设计自己的嵌入方案时对照：

1. **进程内嵌入**，换取零部署拓扑和共享生命周期；运行时三件套版本精确匹配，构建期钉死，不给「就近回退」机会。
2. **启动序列**固定四步：参数、`racket_boot`、载入 `.zo`、取函数调用；boot 文件按平台随包分发，运行时加载。
3. **VM 线程是唯一通道**：所有 Racket 调用在 VM 线程执行，宿主请求在边界排队，激活与停放配对。
4. **编组三职责**：类型翻译、内存归属、错误传播；`ptr` 只是借眼看，GC 归 Racket。
5. **契约先行**：接口用宏声明一次，两端代码生成；传输走长度前缀的二进制帧，异步用事件回推。
6. **分发矩阵交给 CI**：平台 × 架构 × 运行时自动出产物，不让手工构建成为平台的天花板。

想看这套模式的完整开源实现，[Noise](https://github.com/Bogdanp/Noise) 是最好的范本——从 C 层运行时、二进制序列化协议到 DSL 代码生成，每一层都可读。想看逐字节的启动细节，不妨自己动手：解包任何一个 Racket 安装目录，三件套就在那里。

## 结语

这本书从「写几行文字，电脑就会动」开始，一路走到了语言工场：你能造类型、造控制流、造语言，现在你也知道，这些语言和程序可以住进任何宿主、交付给任何用户。

Racket 的终极形态从来不是「又一个脚本语言」，而是**应用逻辑的通用底座**：宏系统让你定制语言，契约让你跨越边界，嵌入让你进入原生世界。工具已经在你手里，剩下的问题只有一个——你想造点什么？
